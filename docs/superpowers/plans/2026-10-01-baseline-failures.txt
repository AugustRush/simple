# Frozen baseline failure set

Command: `.venv/bin/python -m pytest -q -p no:cacheprovider --tb=no`

Any run whose FAILED set differs from this list has been changed by the work in
progress. Update this file only when the environment changes, and say so —
never to accommodate a regression.

## Current baseline — re-measured 2026-10-15, after the pluginization round

```
19 failed, 4116 passed, 2 skipped, 333 warnings in 118.44s (0:01:58)
```

**Every entry is now a thing this machine cannot do.**  That is the property worth keeping:
a baseline is a list of environment limits, and a real bug hiding in one is how the MCP
cross-loop teardown survived here unnoticed.  Two entries have been removed by fixes
rather than by an environment change, and both are recorded below.

**Measured again under `danger-full-access` (2026-10-15):**

```
3 failed, 4145 passed, 2 skipped
```

Only the three console-width probes failed; every entry attributed to `sandbox_apply` above
**passed** when the file policy allowed it.  That is the independent confirmation the
classification was right -- the 16 sandbox entries are the file policy talking, not the
code -- and it is the reason the reasons below are written per entry instead of as a count.
A baseline captured under one policy must only be compared against a run under the same one.

Reasons:

* `sandbox_apply` — `sandbox-exec: sandbox_apply: Operation not permitted` (12 tests).
  This run's file policy is `workspace-write`; the sandbox set disappears under
  `danger-full-access` and comes back here.  Compare against the baseline captured under
  the *same* policy.
* `console width` (3 tests) — terminal-size probing in a non-interactive harness.
* `output-dir sandbox write`, `user tool isolation` (3 tests) — the same sandbox cause.
* `tests/test_agent_integration.py::test_build_components_loads_user_tool_plugins` — a user
  tool's subprocess is refused by the sandbox, so the tool returns
  `{'error': ... 'sandbox_apply: Operation not permitted'}`.

**Removed by a fix:**
``tests/test_mcp_plugin.py::test_the_real_composition_gets_mcp_client_from_the_plugin``
was not an environment failure but a real one -- `MCPClient.close()` gathered tasks
belonging to another event loop -- fixed in `4dc7ddf`.
``tests/test_web_channel.py::test_the_artifact_listing_skips_a_file_that_vanishes_mid_listing``
was a *test* that stopped staging its own race under Python 3.14 (`Path.is_file` does not go
through the monkeypatched `Path.stat`), so it reported a product bug that was not there; the
fixture now stages through `os.stat`.
